# Golden-master harness (BUILD_SPEC 7.1)

Records what the **untouched** desktop engine (git tag `baseline-engine`, upstream v4.6.1) produces for each ROM, settings profile and seed. Every later version (`:core`, then the Android app) must reproduce these hashes exactly.

## Run it (Windows)
From the repository root, in PowerShell:
```bash
powershell -ExecutionPolicy Bypass -File tools\golden\run-baseline.ps1
```
Quick smoke test first (3 cases per ROM instead of 12):
```bash
powershell -ExecutionPolicy Bypass -File tools\golden\run-baseline.ps1 --only none,typical
```
Linux/macOS: `tools/golden/run-baseline.sh` with the same options.

Options: `--gens 4,5` (only those generations), `--only id1,id2` (profiles), `--timeout-min N` (per process, default 20), `--xmx 4608M` (Java heap, default as desktop), `--keep-outputs` (keep randomized ROMs in `testroms/golden-work/jobs` for boot tests).

## Excluding files
`exclude.txt` lists files under `testroms/` that must not be used (for example a ROM that is already randomized). They are skipped and recorded as NOT VERIFIED in the manifest.

The PowerShell script uses the first JDK that actually runs, from: `JAVA_HOME`, `javac` on PATH, `C:\Program Files\Android\Android Studio1\jbr`, `C:\Program Files\Android\Android Studio\jbr`.

## What it does
1. Refuses to run if `src/` differs from `baseline-engine`.
2. Compiles the engine (minus the Swing GUI and launcher) with **UTF-8** source encoding and a one-class shim for `NewRandomizerGUI` (`shim/`), so nothing in `src/` is changed. The shim's location makes the engine's `ROOT_PATH` = `testroms/golden-work/root/`.
3. Finds every ROM under `testroms/` (any depth, by extension), except in `testroms/updates/`, which is for 3DS game update `.cia` files.
4. For each ROM and each case (profile + seed from `profiles.tsv`): runs it in a **fresh JVM twice**, then runs all cases again **one after another in one JVM**.
5. Writes `manifests/baseline.tsv` and prints PASS / FAIL / NOTHING VERIFIED.

The call sequence copies the desktop GUI (`NewRandomizerGUI.performRandomization`), including `romHandler.setLog`, not the CLI. See `java/uprzx/golden/GoldenCase.java`.

## Results
- `manifests/*.tsv` — committed. Hashes, settings strings, seeds, check values. **No ROM data.**
- `testroms/golden-work/logs/` — full randomization logs (with UTF-8 BOM like desktop). **Not committed** (they describe ROM contents). Compare logs from run A and run B here when investigating a mismatch. Each process's error output (engine stack traces) is saved there as `stderr__<rom>__<profile>__<seed>.txt`.
- Compared between runs: `status, romSha256, gen, romName, romCode, romValid, tweak flags, customNamesSha256, settings, checkValue, outputSha256, outputBytes, logSha256, error`.
- Diagnostic only: `elapsedMs, peakHeapBytes, tempFilesOnDisk, tempBytesPeak`.
- Log normalisation: line endings to `\n`, and the `Time elapsed:` line removed. Nothing else is excluded.

Exit codes: 0 pass, 1 mismatch between runs, 2 nothing verified (no ROMs, or none loaded). A case that ends in an engine error is recorded as such; it still counts as deterministic if both runs fail the same way, and is reported for review.

## Profiles
`profiles.tsv` is generated by `java/uprzx/golden/Profiles.java` (`run-baseline.sh --regenerate-profiles`). They are inputs for checking engine equivalence; some combinations may be ones the desktop GUI would not allow. `none`, `typical`, `max`, `modes-1`..`modes-5` (together with `none`, every value of every mode enum), `misc-all`, `limit-gen1`, `legacy-update`.
